# GITHUB_RULES — commit / push / changelog / README更新のルール

<!-- 運営OS版のGit運用ルール。毎日の保存作業はこのファイルだけ見ればできる -->

## 毎日の保存手順(終業前・5分)

```bash
# 1. 変更を確認する(何を保存するか自分の目で見る)
git status
git diff --stat

# 2. ステージして、その日のDAYファイル推奨メッセージでコミット
git add -A
git commit -m "Day◯◯: (推奨コミットメッセージ)"

# 3. プッシュ(週1ではなく毎日。今日の成果は今日リモートへ)
git push
```

## commitのルール

- **1日の作業終わりに最低1コミット**(大きな区切りごとに分けるのが理想)
- メッセージ形式:`Day◯◯: 何をしたか(英語または日本語・50字以内)`
  - 例:`Day04: 自社LP v1を完成(HTML/CSS実装+検品済み)`
- 「fix」「update」だけのメッセージ禁止/1コミットに無関係な変更を混ぜない
- 認証情報・クライアント機密が含まれていないか `git diff` で確認してからコミット

## pushのルール

- コミットしたら必ずその日のうちにpush(ローカルだけの資産を作らない)
- push失敗(ネットワーク)は時間を置いて再試行。翌日に持ち越さない
- 作業ブランチ運用中は `git push -u origin ブランチ名`

## CHANGELOGのルール

- 場所:`12_OPERATING_SYSTEM/CHANGELOG.md`
- **push後に1行追記**(これが「今日をやった」証明であり、明日の朝の道しるべ)
- 形式:`| 日付 | DAY◯◯ | やったこと | 状態(完了/持ち越し) |`
- 持ち越しの場合は「どこまで進んだか」を書く(明日の自分への引き継ぎ)

## README更新のルール

- 新しいフォルダ・製品・大きな構造変更をしたら、**同じコミットで**ルート `README.md` を更新する
- 各フォルダのREADMEも同様(フォルダの中身とREADMEのズレは信頼性の死)
- 製品の版が上がったら:製品README+`06_PRODUCTS/07_RELEASES/release_log.md` も更新

## 週次(Day07/14/21/28)の追加作業

- `git log --oneline` で1週間の履歴を見返す(週次レビューの材料)
- mainへの統合(ブランチ運用中の場合)を検討する
